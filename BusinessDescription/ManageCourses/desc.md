# Business Use Case: Quản lý khóa học

| Trường thông tin | Nội dung |
| --- | --- |
| **1. Tên Use case** | Quản lý khóa học |
| **2. Tóm tắt** | Quy trình quản lý toàn bộ vòng đời khóa học từ khi Giảng viên tạo khóa học mới, chỉnh sửa nội dung, đến khi Admin phê duyệt và khóa học được mở bán trên hệ thống. Bao gồm việc tạo, chỉnh sửa, tạm dừng và xóa khóa học. |
| **3. Tác nhân** | **Giảng viên** — Người trực tiếp tạo và quản lý nội dung khóa học. / **Quản trị viên (Admin)** — Người phê duyệt khóa học, quyết định khóa học được mở bán trên hệ thống. |
| **4. Use case liên quan** | — **Include:** Không có (Use case độc lập). / — **Extend:** Không có. |
| **5. Dòng sự kiện chính** | 1. **Giảng viên** chuẩn bị thông tin khóa học bao gồm: tên khóa học, mô tả, danh mục lĩnh vực, loại khóa học, giá bán, và kế hoạch nội dung (các phần, bài giảng). / 2. **Giảng viên** tạo khóa học mới trên hệ thống và điền đầy đủ thông tin. / 3. **Giảng viên** thêm nội dung cho khóa học: các phần (Section), bài giảng (Lesson), upload video/tài liệu. / 4. **Giảng viên** hoàn thiện nội dung và chọn thao tác gửi duyệt. / 5. **Admin** nhận thông báo về yêu cầu duyệt khóa học mới. / 6. **Admin** xem xét hồ sơ khóa học: thông tin cơ bản, nội dung bài giảng, giá bán. / 7. **Admin** đưa ra quyết định: **Phê duyệt** hoặc **Từ chối**. / 8. Nếu **Phê duyệt**: **Admin** cập nhật trạng thái khóa học thành "Đang mở bán" trên hệ thống. / 9. **Admin** thông báo quyết định cho Giảng viên. / 10. Use case kết thúc. |
| **6. Dòng sự kiện phụ** | **A1: Khóa học thiếu thông tin** (Tại bước 2) / 1. **Hệ thống** phát hiện khóa học thiếu các trường bắt buộc khi Giảng viên gửi duyệt. / 2. **Hệ thống** hiển thị thông báo lỗi và yêu cầu Giảng viên bổ sung. / 3. **Giảng viên** bổ sung thông tin và gửi lại. / 4. Quy trình quay lại Bước 5. / \-\-\- / **A2: Nội dung khóa học chưa đạt yêu cầu** (Tại bước 6) / 1. **Admin** phát hiện nội dung chưa đạt chất lượng hoặc cấu trúc chưa phù hợp. / 2. **Admin** từ chối và ghi rõ lý do cần chỉnh sửa. / 3. **Giảng viên** chỉnh sửa nội dung theo yêu cầu. / 4. **Giảng viên** gửi duyệt lại. / 5. Quy trình tiếp tục từ Bước 5. / \-\-\- / **A3: Khóa học trùng lặp** (Tại bước 6) / 1. **Admin** phát hiện khóa học đề xuất trùng lặp với khóa học hiện có. / 2. **Admin** từ chối và thông báo cho Giảng viên. / 3. **Giảng viên** chỉnh sửa để tạo sự khác biệt hoặc rút lại đề xuất. / 4. Use case kết thúc. / \-\-\- / **A4: Giảng viên rút lại đề xuất** (Tại Bước 4) / 1. **Giảng viên** chọn thao tác rút lại yêu cầu duyệt trước khi Admin xử lý. / 2. **Hệ thống** hủy yêu cầu duyệt và cập nhật trạng thái khóa học về "Bản nháp". / 3. Use case kết thúc. |
| **7. Điều kiện tiên quyết** | 1. Giảng viên phải đã hoàn tất quy trình đăng ký và được công nhận là Giảng viên chính thức trên hệ thống. / 2. Admin có thẩm quyền phê duyệt cuối cùng đối với mọi khóa học mới. / 3. Hệ thống phải có danh mục lĩnh vực (SubjectCategories) và loại khóa học (CourseTypes) cập nhật. |
| **8. Hậu điều kiện** | 1. Nếu phê duyệt: Khóa học được cập nhật trạng thái "Đang mở bán" trên hệ thống, hiển thị công khai cho Học viên. / 2. Nếu từ chối: Khóa học được đánh dấu "Đã từ chối" kèm lý do, Giảng viên có quyền chỉnh sửa và gửi lại. / 3. Toàn bộ quy trình được ghi nhận trong nhật ký hệ thống để phục vụ tra cứu. |
